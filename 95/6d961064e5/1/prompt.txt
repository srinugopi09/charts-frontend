# Commit

Create a git commit by analyzing staged and unstaged changes, drafting a concise commit message, and committing.

## Workflow

1. Run in parallel:
   - `git status` (never use `-uall`)
   - `git diff` and `git diff --cached` to see all changes
   - `git log --oneline -10` to match the repo's commit style

2. If there are no changes to commit, inform the user and stop.

3. If the user provided a message argument, use it as the commit message. Otherwise, draft one:
   - Summarize the nature of the change (feature, fix, refactor, docs, test, etc.)
   - Use imperative mood ("Add X" not "Added X")
   - Keep the first line under 72 characters
   - Add a blank line and brief body only if the change is non-trivial
   - Focus on *why*, not *what*
   - Do not add co-authored by

4. Stage relevant files by name (avoid `git add -A` or `git add .`). Skip files that look like secrets (`.env`, credentials, keys).

5. Commit using a HEREDOC for proper formatting:
   ```bash
   git commit -m "$(cat <<'EOF'
   Commit message here

   
   EOF
   )"
   ```

6. Run `git status` after committing to verify success.

7. If a pre-commit hook fails: fix the issue, re-stage, and create a **new** commit (never `--amend`).

## Rules

- Never `git push` unless the user explicitly asks
- Never amend, force-push, or run destructive git commands
- Never skip hooks (`--no-verify`)
- Never use interactive flags (`-i`)
- Never commit `.env`, credentials, or secrets
- Do not append `Co-Authored-By: Claude Opus 4.6 <noreply@anthropic.com>` to the message
